- (constraint) The PRD is the driving input and governs a web-only, responsive, zero-install CRM for small hotels; the spine covers the whole product at initiative altitude.
- (constraint) Existing repository reality contains planning artifacts and a standalone assets/styles.css, but no application runtime, package manifest, persistence layer, or deployment configuration; the architecture must not pretend an implementation stack exists.
- (decision) Use a modular monolith with hexagonal boundaries: feature modules own business rules, ports define external contracts, adapters isolate channels and infrastructure, and a shared domain event path handles asynchronous synchronization and automation. This prevents independently built capabilities from creating competing owners or bypassing business invariants.
- (decision) Booking and room inventory are the single source of truth for availability; every channel integration must converge through the booking/inventory application boundary, and no UI or channel adapter may write competing availability state. This prevents double-booking logic from diverging across channels.
- (decision) All business mutations enter application commands, emit an auditable domain event, and are attributed to an actor or integration; asynchronous consumers must be idempotent and expose stale/failed status. This prevents silent writes, duplicate sync effects, and false certainty during channel outages.
- (decision) Guest, booking, room, pricing, communication, reporting, automation, access, and property configuration are separate modules with explicit contracts; shared kernel is limited to identifiers, time, money, actor, and error primitives. This prevents a catch-all shared model from coupling unrelated capabilities.
- (decision) Authorization is enforced at the application boundary for every command and query using property-scoped roles; adapters and UI affordances are not security boundaries. This prevents role drift and unauthorized mutation of rates, settings, guest data, and user access.
- (assumption) [ASSUMPTION] A relational transactional store is the default persistence shape because bookings, room occupancy, money, audit records, and role-scoped changes require transactional consistency; the concrete engine is deferred until implementation constraints are known.
- (assumption) [ASSUMPTION] A durable job runner/queue is required for channel sync, scheduled pre-arrival messaging, pricing evaluation, retries, and fallback delivery; provider choice is deferred.
- (question) Open: choose the implementation stack, hosting provider, database engine, queue/job technology, and concrete channel APIs after the first build slice and operational constraints are known.
- (question) Open: define the exact channel conflict-resolution policy and reconciliation authority for simultaneous external updates before channel adapters are implemented.
- (event) Fast-path architecture run activated for the whole hotel CRM; assumptions are explicit for review.
- (decision) Refine ownership: booking owns reservations, overlap decisions, room assignment, and sellable availability; inventory owns room definitions and operational readiness only. Availability is a booking projection over inventory rooms, not a second inventory-owned booking state.
- (decision) Use a transactional outbox or equivalent atomic event publication: command state and event intent commit together, workers claim events/jobs with leases, consumers enforce idempotency, and projections expose last-applied position or freshness. This prevents lost events, duplicate effects, and incompatible retry behavior.
- (decision) Every persisted business record, job, projection, cache key, and external credential reference is property-scoped; cross-property access is denied by default. Dates use the property's IANA time zone for business rules while persisted instants remain UTC; money is integer minor units plus ISO currency.
- (decision) The deployment envelope requires separate development, test, and production configuration; secrets stay outside source control; health/readiness checks, structured logs, metrics for sync and job freshness, backups, and operator-visible degraded states are mandatory capabilities before production.
- (event) spine finalized after lint and reviewer-gate fixes

- (decision) Adopt the material-starter responsive shell as the interface seed: drawer at large widths, rail at medium widths, and bottom navigation at compact widths. Pages reuse the starter tokens/components and do not invent page-local colors, typography, or component primitives.
