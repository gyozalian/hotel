- (constraint) The PRD, product brief, addendum, and UX artifacts define a web-only, responsive, zero-install CRM for small guest houses and boutique hotels; v1 is staff/admin-facing and excludes native apps, multi-property rollups, predictive forecasting, deep accounting, guest portal, and multilingual support.
- (constraint) The repository contains planning artifacts and static visual assets but no application runtime, package manifest, persistence layer, or deployment configuration; the spine must keep implementation technology as seed or deferred rather than pretend it exists.
- (constraint) The Material starter under docs/planning-artifacts/ux-designs/material-starter is the visual interface seed: dashboard.html is the reference page and tokens.css/components.css govern responsive shell and component reuse.
- (decision) Use a modular monolith with hexagonal boundaries: interface and transport depend on application use cases; application orchestrates commands, queries, authorization, and transactions; domain modules own business rules; ports isolate persistence, channels, messaging, scheduling, and observability; adapters implement ports. This prevents independently built capabilities from bypassing business invariants or coupling to providers.
- (decision) Booking is the sole authority for reservations, room assignment, overlap decisions, and sellable availability; inventory owns room definitions and operational readiness only. All manual and external booking changes enter booking application commands. This prevents conflicting availability calculations and double-booking logic.
- (decision) Each business entity has one owning module: booking, inventory, guest, pricing, communication, automation, access, property, and reporting. Other modules consume versioned commands, queries, events, or projections and never write another module’s tables. This prevents competing ownership and incompatible data shapes.
- (decision) Separate query and command paths. Queries are read-only; commands authorize, validate, transact, persist, audit, and publish event intent. This prevents read paths from mutating state and keeps transaction boundaries consistent.
- (decision) Every business mutation is property-scoped, attributed to a user or integration, timestamped, and represented by an append-only audit record with correlation and causation metadata. This prevents untraceable operational changes and cross-property leakage.
- (decision) Use a transactional outbox for event delivery: state change and versioned event intent commit atomically; workers claim with leases; consumers use idempotency keys and aggregate sequence; retries, dead-letter status, freshness, and operator replay are visible. This prevents lost events, duplicate effects, and false success.
- (decision) Use property IANA time zones for business dates and schedules, UTC for persisted instants, and integer minor units plus ISO currency for money with one canonical rounding policy. Carry property ID, actor ID, correlation ID, causation ID, aggregate version, and idempotency key across commands and events. This prevents DST, financial, and tenant-boundary divergence.
- (decision) Enforce property-scoped role authorization in the application boundary for every command and query; UI visibility is convenience only. Roles are owner/admin, manager, front desk, housekeeping, and read-only reporting, with sensitive rate, access, channel, and configuration actions explicitly restricted. This prevents security policy drift across interfaces, jobs, and integrations.
- (decision) Treat channel synchronization, messaging, pricing evaluation, automation, reporting projections, and notifications as asynchronous and failure-visible. Provider outages produce stale/offline states, retryable failures, or operator tasks; unresolved availability conflicts fail closed. This prevents silent loss and unsafe availability assumptions.
- (decision) The responsive interface uses one use-case contract across desktop, tablet, and mobile. The Material shell uses drawer at large widths, rail at medium widths, and bottom navigation at compact widths; status uses text plus color, keyboard focus is visible, reduced motion is honored, and interactive targets meet the accessibility floor.
- (assumption) [ASSUMPTION] A relational transactional store is the default persistence shape because bookings, occupancy, money, audit, and role-scoped mutations require consistency; engine selection is deferred until implementation constraints are known.
- (assumption) [ASSUMPTION] A durable job runner is required for channel sync, scheduled automations, pricing evaluation, retries, and fallback delivery; provider selection is deferred.
- (question) Before implementation, choose the language/framework, database, durable job technology, hosting, identity provider, channel APIs, messaging provider, and observability stack; verify current versions and starter defaults before binding them.
- (question) Before channel adapters, define simultaneous-update reconciliation, provider rate-limit behavior, and the operator workflow for unresolved conflicts.
